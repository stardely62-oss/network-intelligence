# Интеграция с Discord Bridge — проект

Статус: **только проект.** В 0.1 Network Intelligence (NI) не читает данные
Bridge, не подключается к его службе и ничего не меняет в его конфигурации.
Bridge и Bridge Catalog в рамках этой работы не изменялись.

Документ основан на публичном коде
[`stardely62-oss/discord-bridge`](https://github.com/stardely62-oss/discord-bridge)
(протокол IPC версии 3, Flowseal 1.10.4) и
[`stardely62-oss/discord-bridge-catalog`](https://github.com/stardely62-oss/discord-bridge-catalog)
(схема наборов 1).

## 1. Что есть в Bridge

| Компонент | Факт | Значение для NI |
|---|---|---|
| Служба `Discord Bridge Helper` (LocalSystem) | канал `\\.\pipe\DiscordBridgeHelper.v1`, кадр «длина + JSON», команды `Hello`, `Status`, `Start`, `Stop`, `Diagnose`, `ListBundles`, `EngineLog`, … | Служба **аутентифицирует клиента по пути образа**: допускается только установленный `discord-bridge.exe`. NI не может и не должен подключаться к этому каналу. |
| `EngineStatus` | `state`, `strategyId`, `strategyName`, `bundleVersion`, `argsPreview`, `configHash`, `trialActive`, `startedAt` | Достаточно для сравнения сессий «до/после» смены стратегии. |
| Настройки UI | `%APPDATA%\io.github.stardely62.discordbridge\settings.json`, стратегии — `…\strategies\*.json` | Файлы пользователя; формат — внутренний, не контракт. |
| Списки | `UserLists { general, exclude, ipsetExclude, ipsetInclude }`, установленные наборы `InstalledPack { id, version, domains, ips, title }`, режим `IpsetMode` (`none`, `selected`, `flowseal`, `flowsealPlusSelected`, `any`) | Это и есть «что идёт через обход». |
| Стратегии | правила winws с `--filter-tcp`/`--filter-udp` (порты), `--hostlist`, `--ipset`, `--filter-l7` | Определяют, какие **порты и протоколы** вообще попадают под обход. |
| Каталог | подписанный Ed25519 снимок наборов (`kind: discord-bridge-catalog`, `serial`), лимиты: ≤ 2000 доменов и 5000 IP на набор, CIDR не шире /8 (v4) и /16 (v6), обязательный `provenance` для IP | Добавление адресов — только через PR в каталог и ревью; автоматически — никогда. |

## 2. Чтение состояния Bridge

Требования: только чтение, без новых прав, без доступа к каналу службы, без
зависимости от внутренних файлов Bridge.

**Предлагаемый контракт — экспорт состояния из UI Bridge** (изменение в Bridge,
отдельная задача):

```jsonc
// Пример ФОРМАТА (значения условные, не реальные данные Bridge)
// %LOCALAPPDATA%\io.github.stardely62.discordbridge\state-export\bridge-state.v1.json
{
  "kind": "discord-bridge-state", "schema": 1,
  "exportedAt": 1794100000000, "bridgeVersion": "0.1.1",
  "engine": { "state": "running", "strategyId": "general-alt2", "configHash": "…", "bundleVersion": "1.10.4" },
  "ipsetMode": "selected",
  "coverage": {                       // что реально захватывает активная стратегия
    "tcpPorts": "80,443,2053,2083,2087,2096,8443",
    "udpPorts": "443,19294-19344,50000-50100",
    "l7": ["discord", "stun"]
  },
  "domains": ["discord.com", "…"],    // эффективные списки после исключений
  "ips": ["162.159.128.0/19", "…"],
  "exclude": { "domains": [], "ips": [] },
  "packs": [{ "id": "discord", "version": 3 }]
}
```

- Файл пишет UI Bridge (обычный пользователь) по кнопке «Поделиться
  состоянием с Network Intelligence» или при изменении, если пользователь это
  включил. Без секретов: в нём нет SID, путей профиля и журналов.
- NI читает файл только для чтения, проверяет `kind`/`schema`, размеры
  (≤ 2 МБ, лимиты как у каталога) и показывает время экспорта — данные
  могут устареть.
- Почему не канал службы: расширять список доверенных клиентов
  привилегированной службы ради чтения нецелесообразно — это увеличивает
  поверхность атаки службы. Если онлайн-чтение всё же понадобится, это должен
  быть **отдельный** канал UI Bridge (не службы), только с командой
  `GetState`, с DACL «только текущий пользователь» и проверкой подписи образа
  клиента.

## 3. Сравнение адресов с наборами Flowseal / Bridge

Вход: адресные группы сессии NI (`AddressGroup`) и состояние Bridge.

1. **IP:** для каждого удалённого IP — поиск в `ips` (CIDR, IPv4 и IPv6,
   IPv4-mapped уже нормализованы NI). Результат: `covered` / `excluded` /
   `notCovered`.
2. **Домены:** в 0.1 у NI нет DNS-имён соединений, поэтому сравнение по доменам
   невозможно. Будет доступно после ETW DNS-Client (0.2): имя → ответ → IP,
   затем `domains` с учётом поддоменов (`*.discord.com` по правилам winws
   hostlist).
3. **Только наблюдаемое:** сравниваются адреса, которые NI видел у процесса;
   отсутствие IP в сессии не означает, что приложению он не нужен.

## 4. Несовпадения портов и протоколов

Типовые ситуации, которые можно выявить по данным NI + `coverage`:

| Наблюдение NI | Состояние Bridge | Вывод (гипотеза, не факт) |
|---|---|---|
| TCP к IP из `ips`, порт не входит в `tcpPorts` | обход включён | адрес в списке, но порт не захватывается стратегией |
| UDP-привязки процесса есть, `udpPorts` пуст | любая | голос/QUIC не обрабатывается стратегией (в 0.1 удалённые UDP-адреса не видны — только «приложение использует UDP») |
| IPv6-endpoints к адресам, которых нет в `ips` (только IPv4-подсети) | `selected` | IPv6-трафик идёт мимо IP-набора |
| Застрявший SYN_SENT к IP вне `ips` | `selected` | кандидат на добавление — после проверки |

Каждое такое сопоставление оформляется как `Finding` категории
`controlComparison` с источниками `observed_process` и (новым) `bridge_state`,
с уверенностью не выше «низкой».

## 5. Экспорт проверенных кандидатов для Bridge

NI **никогда** не добавляет адреса в Bridge или каталог сам.

1. Пользователь отмечает адреса в «Соединениях» как кандидаты.
2. NI формирует файл `ni-candidates.v1.json`:
   ```jsonc
   // пример формата
   { "kind": "network-intelligence-candidates", "schema": 1,
     "application": "Discord.exe",
     "candidates": [
       { "ip": "162.159.130.234", "ports": [443], "protocol": "tcp",
         "evidence": { "sessionId": "…", "endpointIds": [12], "firstSeen": 0, "lastSeen": 0,
                       "observations": 14, "probe": "connected|timedOut|…" } }
     ] }
   ```
   Только публичные адреса (`scope = global`), только одиночные IP (не
   подсети) — расширение до подсети требует источника (`provenance`), как в
   правилах каталога.
3. Bridge импортирует файл в «IP через обход» **с подтверждением** (показ
   списка, валидация теми же правилами `lists::validate`). Для каталога — PR
   с указанием источника.

## 6. Сравнение сессий до и после смены стратегии

- В сессию NI записывается снимок `engine` из состояния Bridge в начале и при
  каждом изменении `configHash` (событие нового типа `bridgeStateChanged`,
  источник `bridge_state`).
- Отчёт «A/B»: две сессии одного приложения, разные `configHash`:
  совпадающие/новые/пропавшие адреса, доля endpoints, дошедших до
  ESTABLISHED, застрявшие SYN_SENT, результаты одинаковых контрольных проверок.
- Ограничение: условия сети между сессиями меняются; сравнение показывает
  корреляцию, а не причину.

## 7. Безопасность IPC

| Требование | Как |
|---|---|
| Нет новых привилегий | обмен через файлы пользователя или канал UI-процесса Bridge, не службы |
| Нет записи NI в Bridge | NI только читает `bridge-state`; кандидаты передаются файлом, импорт — действием пользователя в Bridge |
| Подлинность | проверка `kind`/`schema`, лимитов; для канала — `PIPE_REJECT_REMOTE_CLIENTS`, DACL текущего пользователя, проверка пути и подписи образа сервера/клиента (`GetNamedPipeServerProcessId`) |
| Устаревание | `exportedAt` показывается; данные старше сессии помечаются |
| Приватность | в файле нет SID, путей, журналов; NI не включает его в экспорт отчёта без отдельной галочки |

## 8. Объём работ

1. Bridge: экспорт `bridge-state.v1.json` (UI, без изменений службы).
2. NI: чтение и валидация состояния, новый `DataSource::BridgeState`,
   сопоставление IP/портов, `Finding` для несовпадений.
3. NI: экспорт кандидатов; Bridge: импорт кандидатов с подтверждением.
4. NI 0.2: DNS-имена (ETW) → сопоставление доменов.
